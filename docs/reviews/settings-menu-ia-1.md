## 1. 診断

1. **分類が「目的」ではなく「空き」で決まっている。** 遅延の表示が「フォルダとライセンス」に、カウントダウンとスクリーンセーバーが「システム›詳細」に、点滅抑制の表示が「点滅を抑える」（画面）から離れて「システム›詳細」にある。ユーザーは探す場所を推測できない。
2. **「詳細」が 3 つ（操作の詳細・システムの詳細・ブラウン管の詳細）あり、前の 2 つは何でも入れ。** 名前が中身を示さず、しかも満杯なので今後の項目はさらに別の場所へ押し出される（1 の再生産）。
3. **同じ関心事が複数ページに割れている。** 画面の大きさ: サイズ / 画面の形（画面）とフルスクリーン / UI の大きさ（システム›詳細）。一時停止と巻き戻し: 一時停止中の十字キー（操作）・巻き戻し後に一時停止（操作›詳細）・カウントダウン（システム›詳細）・ビデオ演出（画面）。連射: 連射の速さ（操作›詳細）・連射ボタン（タッチ操作）・連射›（アーケード）。
4. **一度決めたら触らない項目が最前面にある。** 画面の 1 段目にビデオ演出・点滅を抑える、システムの 1 段目に言語・Steam に追加。一方で毎回触りうる音量は 1 項目だけのページ、よく変えそうなフルスクリーンは深さ 3。
5. **ページの密度が偏っている。** ABXYボタン（2 項目）、音（1〜3）、画面の形（3）、連射（3）は薄く、画面・操作・操作›詳細・システム›詳細は満杯。薄いページが「ページが多い」感覚を、満杯のページが「どこへ足すか分からない」を生む。
6. **深さが規則を超えている**（上記、4〜5 段）。アーケードの連射はボタンごとにページを生成し、ボタンの数だけページが増える。
7. **名前。** 「ReplayNESのバージョン」がアップデート操作とフォルダを含む。「ABXYボタン」から決定ボタンの設定だと分からない。「使用するコア」「電源のたわみ」「線の太り」「電波の強さ」「スティックのしきい値」は内部・愛好家の語。「連射の押す長さ」「周期」「押す長さ」はフレーム単位の調整で一般ユーザーには意味が取れない。
8. **開発・計測向けの項目が一般ユーザーの木に混ざっている。** 遅延の表示（説明に「F3」とあり、キーで出せる）、設定ファイル（パス表示のみ）、走査線（説明が「240 = standard; fewer lines is an experiment」）。
9. 技術面の煩雑さ: 上記の moveOsk / 重複 ID は、木が宣言だけで決まらない原因。整理後はこれを消せる。
10. 設定外だが一言: 共有タイルは Steam Deck では「動画にする」1 項目だけのページを開く（fixture `share:share.export`）。タイルを直接アクションにすれば 1 ページ減る（推測: 配信出力のある macOS だけページのまま）。

### 案 C — 既定値で足りる項目を削り、木を小さくする（B に重ねる）

## 3. 削る・統合してよい候補と、危ない項目

削ってよい（UI から外す。設定キーは残す）:

- **遅延の表示** — 説明に「F3」とあり、キーで出せる開発向け計測。置き場が「フォルダとライセンス」なのは既に居場所が無い証拠。
- **点滅抑制の表示** — 点滅を抑える のバッジ可否。既定で十分（推測）。残すなら 点滅を抑える の選択肢に「強（表示あり）」のように畳む方が自然。
- **設定ファイル**（INFO）— パス表示のみ。フォルダとライセンス の説明文か、プロジェクトフォルダ の値欄に寄せられる。
- **連射の押す長さ**／**周期**／**押す長さ**（フレーム単位）— 一般ユーザーに意味が取れない。連射の速さ だけ残し、長さは速さから導く（推測: 現在の既定値の比率で）。アーケードのボタンごと連射は「全体 / 個別」の 2 択だけ残し、個別は 速さ 1 本に。
- **ブラウン管›既定に戻す** — Y ボタンへ（上記）。
- **ABXYボタンの位置合わせ** — コントローラー ページ内の操作（X=次のパッド の隣）へ寄せる候補。FACE_CHECK.md が「Controller の下に置かない（リセットで消えないように）」と決めているので、その理由を確認してから。
- **追従（上下）／追従（左右）** — 1 本の「追従」に統合できれば タッチ操作›十字キー を親へ畳める（深さ 4 → 3）。キーは 2 つのまま同じ値を書けばよい。

統合:

- **ブラウン管（入/切）＋ブラウン管の詳細** → 1 ページ「ブラウン管」（1 行目が入/切）。
- **ABXYボタン（2 項目）** → ページを解き、決定ボタン を 操作 直下へ。
- **ReplayNESのバージョン** → 名前を「アップデート」に（中身がそれ）。バージョン と 状態 は 1 行に併記できる（推測: INFO 行の値欄に文字列）。

削るのが危ない:

- **点滅を抑える**（光過敏への配慮。目立つ場所に残す）。**決定ボタン**（任天堂配置と Xbox 配置のユーザーが両方いる）。**使用するコア**（「既存の記録は元のコアを保つ」と説明にあり、互換性の判断材料）。**8:7 / 端を隠す**（実機再現を気にする層が触る）。**低遅延・スロー中の音**（機種依存で、既定が合わない環境の逃げ道）。**自動保存**（遅いストレージの逃げ道。ただし 2 択に減らす余地はある）。**操作をリセット**（割り当てを壊したときの復旧手段）。**言語**。

## 4. 推奨

**案 B を採り、案 C のうち「遅延の表示・点滅抑制の表示・設定ファイル・ブラウン管›既定に戻す」の 4 つだけを同時に外す**（他の削除は様子見）。

理由:

- 診断 1〜3 の根は「空いている場所へ置く」運用で、案 A の「その他」はその運用を名前を変えて続けるだけ。B は置き場の規則（画面の大きさは画面、一時停止と巻き戻しは プレイ、配布と環境は アプリ）を木そのものに持たせるので、次の項目を足すときも迷わない。
- B は操作・プレイに空きが残り、満杯ゆえの押し出し（moveOsk、重複 ID）を消せる。コードも宣言的に戻る。
- 4 つの削除は、いずれも開発向けか代替手段（F3、Y ボタン、説明文）があるもので、ユーザーの動作が変わらない。残りの削除（フレーム単位の連射、追従の統合）は値の意味が変わるので、別の回で設計してから。
- 移行で危険な所は無い: 項目 ID・設定キーは不変、ui_settings.cpp の分岐はそのまま使える。壊れるのは期待値を持つテスト（fixture、test_frontend_menu.cpp、QuickMenuModelTests.swift）だけで、それは意図した変更。

次に確かめるべきこと（実装前）: SETTINGS ページで Y ボタンを「既定に戻す」に使えるか（コントローラー図の実装 `controls.controller` CUSTOM ページを参照）、INFO 行の値欄に状態文字列を併記できるか、FACE_CHECK.md が位置合わせの置き場に課している条件、クイックメニュー「設定」タイルの説明文と初回起動（UI_REDESIGN.md「First run」）が設定ページ名を参照していないか。
